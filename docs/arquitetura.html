Arquitetura técnica

Como as peças do Hub de Projetos se organizam e conversam, e por que cada uma existe. A ideia principal é manter o sistema simples: um comando sobe tudo, e a regra de acesso fica em um só lugar.

1 As peças do sistema

O Laravel é o centro: só ele conhece as regras do negócio e fala com o banco de dados para valer. Os outros serviços cuidam de tarefas específicas e sempre perguntam ao Laravel antes de liberar algo.

Navegadoro app em React

↓ repassa conforme o caminho

Por que um único endereço?

A pessoa abre http://localhost:5173 e o Vite repassa /api, /app e /collab para cada serviço. Para o navegador, tudo vem do mesmo lugar, então o login por cookie funciona e não é preciso configurar CORS. O LiveKit é a exceção: o navegador conecta direto nele.

Por que não usar microsserviços?

O sistema é feito por uma pessoa e atende até cerca de 50 usuários por setor. Um Laravel único, com o código separado por módulo, atende à RNF17 sem a complexidade de vários back-ends.

2 Serviços do Docker

Cada linha é um contêiner, como um pequeno computador com uma função só. O docker compose up liga todos eles juntos.

ServiçoO que fazPorta

Sem Redis no começo. Ele é comum em projetos Laravel, mas a fila pode ficar no próprio PostgreSQL, e o Reverb não precisa dele com um só servidor. É uma peça a menos para entender e manter. Se a fila ficar lenta, ele entra depois.

Na primeira execução

O serviço api instala as dependências, cria as tabelas e carrega os dados de exemplo sozinho, se o banco estiver vazio. Assim, quem testa não precisa rodar nenhum comando a mais (RNF15).

git clone <link-do-repositório>
cd hub-de-projetos
cp .env.example .env
docker compose up

# Sistema:  http://localhost:5173
# E-mails:  http://localhost:8025

Back-end: MVC com Services (D36)

O Laravel já é MVC. Como a tela fica no React, o "V" passa a ser o JSON montado pelos API Resources. A regra de negócio fica nos Services, e não nos controllers, porque uma ação como "superior edita tarefa" faz várias coisas na mesma transação: salva, registra a auditoria, notifica o dono e avisa o Reverb. Assim, o controller continua curto.

Front-end: organizado por módulo (D37)

Primeiro vem o assunto (kanban/), depois o tipo (components/, hooks/). Tudo de uma funcionalidade fica em uma pasta só, os módulos têm os mesmos nomes do back-end, e um módulo pode ser adiado ou removido sem procurar arquivos pelo projeto todo (RNF17, D19). Se um módulo importar algo de outro, isso precisa ir para compartilhado/.
Nomes em português nas regras do negócio. O modelo de dados já usa tarefas e reunioes, então as classes seguem o mesmo vocabulário: Tarefa, Reuniao. O que vem do framework continua em inglês, como Controller e Policy. Como o Laravel espera tabelas em inglês, cada Model informa o nome da tabela com $table.

4 Regra de acesso no código

É a parte mais importante do sistema. A consulta da seção 9 do modelo de dados fica em um único lugar, e todo o resto chama esse lugar (RNF21).

// backend/app/Acesso/Item.php (esboço)
public function scopeVisivelPara(Builder $query, Membro $eu): Builder
{
    // Aqui fica a regra (a), (b) e (c) dos requisitos, e em nenhum outro lugar
}

// Toda listagem usa a regra, em vez de escrever o próprio filtro
Item::visivelPara($eu)->where('tipo', 'tarefa')->get();

Listas e buscaItem::visivelPara($eu)
Abrir, editar e excluir um itemUma Policy do Laravel, que usa a mesma regra
Canais ao vivoO Reverb pergunta ao Laravel se a pessoa pode entrar no canal
Documentos em conjuntoO Hocuspocus pergunta ao Laravel antes de conectar
Sala de vídeoO Laravel só gera o token do LiveKit para quem pode ver a reunião
Download de arquivoO arquivo só sai pelo Laravel, depois da verificação (RNF04)
O React nunca decide o acesso. Ele pode esconder um botão para a tela ficar mais limpa, mas quem garante a regra é o back-end (RNF02). Quem chamar a API diretamente recebe a mesma resposta.

Auditoria automática

Quando uma Policy libera uma ação porque a pessoa é superior, e não porque é dona do item, o Laravel registra a auditoria e notifica o dono na mesma transação do banco. Assim, ninguém altera um item de subordinado sem deixar registro, nem mesmo por esquecimento de quem programou. A proteção contra apagar registros continua no próprio banco.

5 Login e segurança

Login por cookie (Laravel Sanctum)

Depois de entrar, o navegador guarda um cookie de sessão que o JavaScript não consegue ler. Isso protege melhor contra roubo de sessão por XSS do que guardar um token no localStorage. O Sanctum também cuida da proteção contra CSRF.

Conversa entre os serviços

O Hocuspocus chama uma rota interna do Laravel, protegida por uma senha compartilhada que fica no .env. Essa rota não é repassada pelo Vite, então o navegador não tem como acessá-la.
RequisitoComo é atendido
RNF01: senhasHash do próprio Laravel
RNF05: injeção, XSS e CSRFConsultas do Eloquent com parâmetros, escape automático do React e Sanctum
RNF05: limite de tentativasRate limiter do Laravel na rota de login

6 Os caminhos principais

Mover uma tarefa no kanban

  1. O card muda de coluna na tela da pessoa na hora, antes da resposta do servidor. Se o servidor recusar, ele volta.
  2. O React envia a mudança para o Laravel, que verifica a permissão e salva.
  3. O Laravel avisa o Reverb: "a tarefa 128 mudou neste quadro".
  4. O Reverb repassa o aviso a quem está no quadro.
  5. Cada navegador pede a tarefa 128 ao Laravel, que aplica a regra de acesso para aquela pessoa.
Por que o aviso leva só o número da tarefa? Um quadro pode ter tarefas privadas. Se o aviso levasse título e responsáveis, os dados chegariam a todos no quadro, mesmo sem aparecer na tela. Levando só o número, quem não tem acesso recebe uma recusa ao pedir a tarefa, e nada vaza (RNF20). Custa uma chamada a mais, mas o tempo deve caber na meta de cerca de 1 segundo (RNF25). Vamos medir isso na construção.

Editar um documento em conjunto

  1. O React pede ao Laravel um token temporário para aquele documento.
  2. O navegador conecta no Hocuspocus com o token, e ele confere com o Laravel se a pessoa tem acesso.
  3. Cada edição vira uma pequena mudança do Yjs, enviada às outras pessoas. O Yjs mescla edições simultâneas sem perder texto (RNF26).
  4. O Hocuspocus salva o estado no banco, em documentos.estado_colaborativo, alguns segundos depois da última edição.
  5. Quando todos saem, o Hocuspocus avisa o Laravel, que cria a versão da sessão em documento_versoes (RNF29, D21). Se um superior editou, a auditoria aponta para essa versão.
Se alguém perder o acesso (RNF28): o Laravel avisa o Hocuspocus, que desconecta a pessoa na hora. Na queda de conexão (RNF27), o Yjs continua registrando o que a pessoa escreve e sincroniza quando ela voltar.

Entrar em uma reunião

  1. A pessoa clica em Entrar, e o React pede um token ao Laravel.
  2. O Laravel verifica se ela pode ver a reunião e gera um token do LiveKit válido só para aquela sala.
  3. O navegador conecta direto no LiveKit com o token, e o áudio e o vídeo não passam pelo Laravel.

Enviar um arquivo

  1. O Laravel verifica a permissão, o tamanho (até 50 MB) e o tipo do arquivo.
  2. Ele salva o conteúdo no volume, com o sistema de arquivos do Laravel, e guarda só a referência em arquivos.chave_storage.
  3. O envio não depende de onde o arquivo fica: para trocar o disco por um serviço como o S3, muda só a configuração (RNF18).

7 Testes

O que testarFerramentaPrioridade

Análise estática e padrão de códigoLarastan e Pint · TypeScript strict, oxlint e PrettierSempre, no comando check
Desenvolvimento guiado por testes (TDD). O teste é escrito antes do código, a partir dos critérios de aceite, seguindo o ciclo vermelho → verde → refatorar. A meta de cobertura é de 80% no geral e de 100% na regra de acesso e nas Policies. O passo a passo está no plano de construção.
Por que testar com PostgreSQL de verdade? A regra de acesso é uma consulta SQL, e os triggers da auditoria só existem no banco. Testar em outro banco poderia passar no teste e falhar no sistema real.

D37Front-end organizado por módulo (primeiro o assunto, depois o tipo), espelhando os módulos do back-end. O que é usado por mais de um módulo fica em compartilhado/.Decidido
D38Fontes do design system com Fontsource (pacotes npm), em vez do Google Fonts: as fontes ficam dentro do projeto e funcionam sem internet.Decidido
D39Lint e formatação do front-end com oxlint + Prettier (decisão revisada em 10/11/2026): o oxlint aponta erros e más práticas, e o Prettier só formata (a mesma divisão de Larastan e Pint no back-end). A primeira versão era ESLint + Prettier, mas a typescript-eslint ainda não suporta o TypeScript 7.Decidido
D40Testes de ponta a ponta na pasta e2e/, na raiz, rodando no serviço e2e do Docker (imagem oficial do Playwright). Ficam fora de backend/ e frontend/ porque atravessam o sistema inteiro. É uma quarta pasta, além das três da D31. O serviço só roda quando é chamado.Decidido
D41O model User fica em Modulos/Conta/Models (namespace App\Modulos\Conta\Models), e não em app/Models. É a D36 sem exceção: tudo de um assunto mora na pasta do módulo, e a pasta app/Models deixa de existir. Ponto contra aceito: pacotes do Laravel assumem App\Models\User, então às vezes será preciso informar o caminho na configuração (como já foi feito em config/auth.php).Decidido
D42Um arquivo de rotas por módulo. Cada módulo do back-end guarda as próprias rotas em backend/app/Modulos/<Modulo>/rotas.php, junto do código que as atende. O backend/routes/api.php vira só um índice, que carrega esses arquivos com require app_path('Modulos/<Modulo>/rotas.php');, e por isso todas as rotas continuam começando com /api. Motivo: é a mesma ideia da D36 (tudo de um assunto na pasta do módulo); com 8 módulos previstos, um api.php único ficaria longo e as rotas ficariam longe do código. Alternativa descartada: todas as rotas no routes/api.php (o padrão do Laravel).Decidido
D43React Router para as rotas do front-end. Cada tela tem endereço próprio (/entrar, /criar-conta), como no wireframe 1, e o botão voltar do navegador funciona. O BrowserRouter fica no frontend/src/main.tsx e a tabela de rotas no frontend/src/App.tsx. Pacote: react-router 8.5.1. Motivo: é o padrão do mercado para React e é compatível com React 19, Node 26 e o TypeScript 7 do projeto (o check passou). Alternativa descartada: trocar de tela com estado do React, sem endereços (o voltar do navegador e os links diretos não funcionariam).Decidido
