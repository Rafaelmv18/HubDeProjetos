1 Antes de começar

O que precisa estar instalado

ProgramaPara quêComo conferir
Docker DesktopRoda o banco, a API, o front-end e todo o restodocker --version
Git (opcional por enquanto)Versionar o código, quando o repositório for criadogit --version

O Docker Desktop precisa estar aberto, com o aviso "Engine running", sempre que você for usar o projeto.

A regra mais importante: as ferramentas do projeto rodam no Docker

O PHP, o Composer, o Node.js, o npm e o PostgreSQL não são instalados na sua máquina. Eles rodam dentro dos contêineres do Docker. Isso garante que o projeto roda igual em qualquer computador.

Por isso, os comandos que você vê em tutoriais não funcionam direto no terminal do Windows. Eles ganham um prefixo que diz "rode isto dentro do contêiner":

Em tutoriais você vêNeste projeto você usa
php artisan serveNada: já roda sozinho no serviço api
php artisan migratedocker compose exec api php artisan migrate
composer installdocker compose exec api composer install
vendor/bin/pestdocker compose exec api vendor/bin/pest
npm run devNada: já roda sozinho no serviço web
npm install <pacote>docker compose exec web npm install <pacote>
npm run lintdocker compose exec web npm run lint
Mesmo que você tenha o Node instalado no Windows, não rode npm run dev nem npm install nele. O frontend/node_modules/ foi instalado pelo Linux do contêiner, e algumas peças do Vite são feitas só para Linux. No Windows, ele dá erro, e um npm install feito por ele bagunça as dependências do contêiner.
Lendo o prefixo: docker compose exec = "execute dentro de um serviço" · api = o serviço do Laravel (o nome vem do docker-compose.yml) · o resto é o comando normal.

2 Primeira vez

Do zero até ver a API respondendo. Só é preciso fazer isto uma vez por computador.

1. Entrar na pasta do projeto
cd C:\TesteClaude
2. Criar o arquivo de configuração
cp .env.example .env
O .env guarda o nome do banco, o usuário e a senha. O .env.example é o modelo, sem segredos reais.
3. Subir o projeto e esperar
docker compose up -d
Na primeira vez, o Docker baixa as imagens e monta a da API. Depois, a API instala sozinha as dependências, cria o backend/.env, gera a chave e cria as tabelas, e o front-end instala as dependências dele. O comando só devolve o terminal quando tudo estiver pronto.
Tenha paciência na primeira vez: o comando fica parado por cerca de 8 minutos, porque a instalação das dependências da API é lenta no Windows. Parece travado, mas não está. Das próximas vezes, tudo sobe em cerca de 30 segundos.
Opcional: acompanhar o progresso em outro terminal
docker compose logs -f api
Abra um segundo PowerShell na mesma pasta e rode este comando para ver a instalação andando (127/129...). Quando aparecer [api] Pronto. e depois Server running, a API está pronta. Aperte Ctrl+C para sair do log, e a API continua rodando.
4. Ver funcionando

Abra no navegador:

EndereçoO que aparece
http://localhost:5173O front-end (React): a raiz abre a tela de entrar (/entrar)
http://localhost:5173/saudeA página de saúde, que mostra "banco: ok" quando o navegador, o front-end, a API e o banco estão conversando
http://localhost:5173/api/saude{"status":"ok","banco":"ok"}, a resposta do Laravel
Tudo passa pelo mesmo endereço: o Vite mostra a página e repassa o que começa com /api para o Laravel (o "proxy", decisão D30).

3 Dia a dia

Subir o projeto
docker compose up -d
Liga o banco, a API e o front-end, nessa ordem: cada um espera o anterior ficar pronto. Por isso o comando leva cerca de 30 segundos para terminar. Quando ele devolver o terminal, já pode abrir localhost:5173.
Ver o que está rodando
docker compose ps
Mostra cada serviço e o estado dele. O banco e a API devem aparecer como (healthy).
Acompanhar o log
docker compose logs -f api # só a API docker compose logs -f web # só o front-end (Vite) docker compose logs -f db # só o banco docker compose logs -f # todos juntos
O -f segue o log ao vivo. Ctrl+C sai do log sem desligar nada.
Desligar
docker compose down
Desliga e remove os contêineres. Os dados do banco continuam salvos no volume e voltam quando você subir de novo.
Pausar e retomar um serviço
docker compose stop db docker compose start db
Útil para testar o que acontece quando o banco cai: com ele parado, /api/saude responde "fora do ar".
Reiniciar um serviço
docker compose restart api docker compose restart web
A API: quando você mudar o backend/.env ou algo parecer travado. O front-end: quando você mudar o frontend/vite.config.ts.
Reconstruir a imagem da API
docker compose up -d --build
Só é preciso quando o backend/Dockerfile ou o backend/docker/entrypoint.sh mudarem. Mudanças no código PHP aparecem na hora, sem reconstruir.

4 Back-end (Laravel)

Ver todas as rotas da API
docker compose exec api php artisan route:list --path=api

Migrations: aplicar e voltar

Toda migration tem dois métodos, no padrão do Laravel: up aplica a mudança e down desfaz exatamente o que o up fez. Escreva sempre o down de verdade, porque é ele que permite voltar atrás.

Criar uma migration
docker compose exec api php artisan make:migration create_grupos_table
Use nomes descritivos: create_grupos_table, add_prazo_to_tarefas_table. O Laravel coloca a data e a hora no começo do nome, e é essa data que define a ordem.
Ver o SQL antes de aplicar
docker compose exec api php artisan migrate --pretend
Mostra o SQL que seria executado, sem executar nada.
Aplicar
docker compose exec api php artisan migrate
A API já roda o migrate sozinha toda vez que sobe. O comando manual serve para quando você cria uma migration com o projeto ligado.
Ver a lista: o que já rodou e em qual lote
docker compose exec api php artisan migrate:status

Exemplo de como a lista fica:

Migration name ................................ Batch / Status 0001_01_01_000000_create_users_table ............. [1] Ran 0001_01_01_000001_create_cache_table ............. [1] Ran 0001_01_01_000002_create_jobs_table .............. [1] Ran 2026_11_20_100000_create_grupos_table ............ [2] Ran 2026_11_21_090000_add_lider_to_grupos_table ...... [3] Ran 2026_11_21_093000_create_convites_table .......... [3] Ran

Batch (lote) é o número da vez em que o migrate rodou. Tudo o que foi aplicado na mesma execução fica no mesmo lote.

Voltar: escolher quanto desfazer

No Laravel, você não diz "volte até a migration X". Você diz quantas desfazer, a partir da última:

ComandoO que desfaz no exemplo acima
migrate:rollbackO último lote inteiro: convites e lider (lote 3)
migrate:rollback --step=1Só a última: convites
migrate:rollback --step=3As 3 últimas: convites, lider e grupos
migrate:resetTudo, até o banco ficar sem tabelas
Para voltar até uma migration específica: conte quantas linhas existem abaixo dela no migrate:status e use esse número no --step. Para deixar o banco como estava logo depois de create_grupos_table, há 2 linhas abaixo dela, então o comando é --step=2.
Conferir antes de desfazer
docker compose exec api php artisan migrate:rollback --step=2 --pretend
Mostra o SQL dos down que rodariam, sem executar. Depois, rode o mesmo comando sem o --pretend.
Sempre do fim para o começo. Existe o --batch=N, que desfaz um lote do meio, mas evite: desfazer a tabela grupos deixaria a migration seguinte (add_lider_to_grupos_table) marcada como aplicada em uma tabela que não existe mais. Volte sempre a partir da última, como uma pilha de pratos.
⚠️ Voltar desfaz a estrutura, mas não recupera dados. Um down que remove uma tabela ou coluna apaga também o que estava nela.
Neste projeto: a API roda migrate toda vez que sobe. Cada migration nova aplicada assim entra em um lote próprio, e na maior parte das vezes migrate:rollback e --step=1 desfazem a mesma coisa.
Testar código PHP na hora (Tinker)
docker compose exec api php artisan tinker
Um terminal interativo do Laravel. Bom para experimentar consultas, como DB::select('select now()'). Para sair, digite exit.
Mandar um e-mail de teste
Mail::raw('Olá', fn ($m) => $m->to('ana@exemplo.com')->subject('Teste'));
Digite esta linha dentro do Tinker (comando acima) para enviar um e-mail simples pelo Laravel. Ele não sai da máquina: chega na caixa de entrada do Mailpit, que você lê em localhost:8025.
Entrar no contêiner da API
docker compose exec api sh
Abre um terminal dentro do contêiner. Lá dentro, os comandos vão sem prefixo (php artisan ...). Para sair, digite exit.
Dependências (Composer)
docker compose exec api composer install # instala o que está no composer.lock
Para adicionar um pacote novo (composer require), combine antes. A regra do projeto é não instalar nada sem conversar.

Cada pasta tem um README.md explicando o que vai nela. Um módulo nunca importa de dentro de outro: o que é comum vai para compartilhado/.

5 Qualidade e TDD

Rodar os testes
docker compose exec api vendor/bin/pest # todos docker compose exec api vendor/bin/pest tests/Feature/Sistema # só uma pasta docker compose exec api vendor/bin/pest --filter="fora do ar" # só os que têm esse texto no nome docker compose exec api composer test # atalho: limpa o cache de configuração e roda todos
Os testes rodam no banco hub_testes, separado do banco de desenvolvimento. Rodar os testes nunca apaga os seus dados.
Procurar erros sem executar (Larastan)
docker compose exec api composer analyse
Precisa terminar com [OK] No errors. O rigor está no nível 6, configurado em backend/phpstan.neon. O composer analyse é um apelido, definido nos scripts do backend/composer.json, para vendor/bin/phpstan analyse --memory-limit=512M. A opção de memória existe porque, sem o cache (por exemplo, depois de mudar uma dependência), a análise completa não cabe nos 128M padrão do PHP e o Larastan para no meio.
Padrão de código (Pint)
docker compose exec api vendor/bin/pint --test # só verifica, sem mudar nada docker compose exec api vendor/bin/pint # corrige a formatação
Rodar os testes do front-end (Vitest)
docker compose exec web npm run test # roda todos uma vez e termina docker compose exec web npm run test:watch # fica aberto e roda de novo a cada arquivo salvo (Ctrl+C para sair)
O Vitest roda os testes, e a Testing Library testa os componentes como o usuário os usa: achar um botão, clicar e ver o resultado. Os arquivos de teste terminam em .test.ts ou .test.tsx. Enquanto não houver nenhum, o comando termina com "No test files found", e isso é esperado. A preparação que roda antes dos testes fica em frontend/src/test/setup.ts.
Procurar erros no front-end (oxlint)
docker compose exec web npm run lint
Aponta erros e más práticas no código do front-end, como o uso errado de hooks do React. Precisa terminar com 0 erros e 0 avisos. As regras ficam em frontend/.oxlintrc.json.
Padrão de código do front-end (Prettier)
docker compose exec web npm run format:check # só verifica, sem mudar nada docker compose exec web npm run format # corrige a formatação
O Prettier só cuida da formatação (aspas, espaços, quebras de linha). Quem procura erros é o oxlint. É a mesma divisão do back-end: o Larastan procura erros e o Pint formata.
Conferir os tipos e montar a versão final (build)
docker compose exec web npm run build
Roda o tsc, que confere os tipos do TypeScript, e depois o vite build, que monta a versão final do front-end. Isso cria a pasta frontend/dist. Se der erro de tipo, o build para.
Conferir os tipos do front-end sem montar nada
docker compose exec web npm run typecheck
Roda só o tsc. É a parte de conferir tipos do build, sem criar a pasta frontend/dist.
Relatório de cobertura dos testes
docker compose exec api composer coverage # back-end (Pest + PCOV) docker compose exec web npm run test:coverage # front-end (Vitest)
A cobertura mostra quanto do código os testes realmente executam, arquivo por arquivo, e quais linhas nenhum teste tocou. No back-end quem mede é o PCOV, uma extensão do PHP instalada pelo backend/Dockerfile. No front-end, o relatório também sai em HTML, na pasta frontend/coverage/ (abra o index.html dela no navegador). A meta do projeto é 80% no geral e 100% na regra de acesso; o mínimo ainda não é obrigatório, e a cobertura fica fora do check por enquanto.
Testes de ponta a ponta (Playwright)
docker compose run --rm e2e
Um navegador de verdade (o Chromium) abre o sistema e confere o que aparece, com o front-end, a API e o banco no ar. Aqui nada é fingido. O serviço e2e não sobe com o docker compose up -d: o run liga, roda os testes e desliga, e o --rm apaga o contêiner no fim. Precisa terminar com todos os testes em passed. Os testes ficam em e2e/tests/. Na primeira vez, o Docker baixa a imagem do Playwright, que é grande. Se um teste falhar, a gravação do que aconteceu fica em e2e/test-results/.
Conferir tudo de uma vez (check)
.\check.ps1
Roda na raiz do projeto, no PowerShell, com o Docker no ar. Ele executa em sequência a formatação (Pint e Prettier), a análise (Larastan, oxlint e TypeScript) e os testes (Pest e Vitest) dos dois lados, e mostra um resumo com OK ou FALHOU em cada etapa. Ele só confere: não conserta nenhum arquivo. Mesmo que uma etapa falhe, as outras rodam, para você ver todos os problemas de uma vez. É o comando para rodar antes de dar uma tarefa como pronta. Os testes de ponta a ponta (Playwright) ficam de fora, porque são mais lentos.

O ciclo do TDD na prática

PassoO que fazer
🔴 1Crie o teste em backend/tests/Feature/<Modulo>/ a partir de um critério de aceite. Rode o Pest e veja falhar pelo motivo certo (por exemplo, 404 porque a rota ainda não existe).
🟢 2Escreva o mínimo de código para passar. Rode o Pest de novo.
🔵 3Melhore o código com os testes verdes. No fim, rode o Pest, o Larastan e o Pint.

Modelo de teste, seguindo o padrão do projeto (funções do Pest em vez de $this):

<?php use function Pest\Laravel\getJson; it('responde que a API e o banco estão funcionando', function () { getJson('/api/saude') ->assertOk() ->assertExactJson(['status' => 'ok', 'banco' => 'ok']); });
Por que getJson() e não $this->getJson()? Os dois funcionam, mas o Larastan só entende a função. Com $this, ele aponta um erro falso e deixa de conferir o teste.

6 Banco de dados (PostgreSQL)

Entrar no banco pelo terminal
docker compose exec db psql -U hub -d hub
Dentro do psql: \l lista os bancos, \dt lista as tabelas, \d users mostra uma tabela, e \q sai. Comandos SQL terminam com ;.
Rodar uma consulta direto, sem entrar
docker compose exec db psql -U hub -d hub -c "select * from migrations;"

Conectar com um programa (DBeaver, pgAdmin...)

CampoValor
Hostlocalhost
Porta5432
Bancohub (desenvolvimento) ou hub_testes (testes)
Usuário / senhahub / hub_local_123 (valores do .env, só para uso local)

Zerar o banco

⚠️ Apaga todos os dados do banco, sem volta. Use só quando quiser começar do zero.
docker compose down -v docker compose up -d
O -v apaga também o volume, onde os dados ficam. Ao subir de novo, o banco é recriado vazio, o hub_testes volta sozinho e a API recria as tabelas.

8 Problemas comuns

php artisan serve não funciona, ou "php não é reconhecido"

Esperado: não há PHP no Windows (veja a seção 1). A API já está rodando dentro do contêiner quando você dá docker compose up -d. Para outros comandos, use o prefixo docker compose exec api.

npm run dev não funciona, ou "npm não é reconhecido"

Esperado pelo mesmo motivo: o Node.js do projeto existe só no Docker (veja a seção 1). O front-end já roda sozinho no serviço web quando você dá docker compose up -d. Para outros comandos do npm, use docker compose exec web npm .... Se você tiver o Node no Windows e o erro mencionar binding, native ou linux, é porque as dependências são do Linux do contêiner: rode pelo Docker.

"failed to connect to the docker API" ou "dockerDesktopLinuxEngine"

O Docker Desktop está fechado. Abra o programa, espere aparecer "Engine running" e rode o comando de novo.

"Connection refused" ao chamar localhost de dentro do contêiner

Dentro do contêiner, localhost aponta para o IPv6 (::1), e o servidor do Laravel só escuta no IPv4. Use 127.0.0.1:

docker compose exec api wget -qO- http://127.0.0.1:8000/api/saude
http proxy error ou ECONNREFUSED no log do web

O Vite não conseguiu falar com a API. Normalmente isso não acontece, porque o web só sobe depois que a API responde. Se aparecer, a API caiu ou está reiniciando: confira com docker compose ps (ela deve estar (healthy)) e veja o motivo em docker compose logs api --tail 50.

Script .sh falha com "not found" ou um erro com \r

O arquivo foi salvo com a quebra de linha do Windows (CRLF), e o Linux do contêiner só entende LF. No VS Code, clique em CRLF no canto inferior direito, troque para LF e salve. Depois rode docker compose up -d --build.

"port is already allocated" (porta já em uso)

Outro programa está usando a porta (por exemplo, um PostgreSQL instalado no Windows na 5432). Para descobrir qual:

Get-NetTCPConnection -LocalPort 5432 -State Listen

Feche o programa ou combine a troca da porta no docker-compose.yml.

Mudei o .env e nada mudou

.env da raiz (dados do banco): rode docker compose up -d, que recria o que mudou. backend/.env (configurações do Laravel): rode docker compose restart api.

A API não sobe, ou fica reiniciando

Veja o motivo no log:

docker compose logs api --tail 50

Causas comuns: o banco ainda não ficou pronto (espere e confira com docker compose ps) ou um erro em uma migration nova.
