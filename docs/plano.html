Regras do plano

  • Um item só é marcado depois de verificado: rodou, testou, viu funcionar. Escrever o código não basta.
  • Cada etapa termina com a caixa "Etapa concluída", marcada depois de todos os outros itens.
  • Antes de instalar qualquer pacote, o Claude mostra o que vai entrar e espera o seu ok.
  • O que mudar no caminho vai para o Diário e para o documento em docs/.

Definição de Pronto (toda história)

  1. Testes escritos antes do código, a partir dos critérios de aceite dos requisitos
  2. Permissões validadas no back-end, com teste de quem pode e de quem é recusado
  3. Estados de carregando, vazio e erro na tela, cada um com teste
  4. Mensagens em português claro
  5. check todo verde: testes, padrão de código e análise estática
  6. Documento em docs/ atualizado, se algo mudou
  7. Comando novo? Ele entra no guia do desenvolvedor
Onde a marcação fica salva: o que vale é o que está gravado neste arquivo. Quando vocês verificarem um item juntos, o Claude marca no arquivo. Se você clicar em uma caixa aqui no navegador, ela fica amarela ("marcado só neste navegador") até ser registrada.

✓ TDD e QA: como cada coisa é construída

O teste vem antes do código. Ele descreve o que o sistema deve fazer e só depois o código é escrito para cumprir isso. A qualidade é verificada o tempo todo, e não apenas no fim.

O ciclo do TDD

🔴 1. Vermelho

Escreva um teste pequeno para o próximo comportamento. Rode e veja falhar. Se ele passar sem código novo, o teste está errado.

🟢 2. Verde

Escreva o mínimo de código para o teste passar, mesmo que fique feio por enquanto.

🔵 3. Refatorar

Melhore o código (nomes, repetição, Services) com os testes ainda verdes. Depois volte ao 1.
De onde vêm os testes? Dos critérios de aceite de cada história. Cada critério vira pelo menos um teste. Exemplo da US18: "o card volta se o servidor recusar" vira o teste it('devolve o card à coluna original quando a API recusa').

A pirâmide de testes

CamadaO que verificaFerramentaQuantidade
UnidadeUma classe ou função isolada: Services, regras de cálculo, hooksPest · VitestMuitos, e rápidos
IntegraçãoUma rota da API de ponta a ponta com o banco real: permissão, validação e resposta. Também os 9 cenários de acessoPest + PostgreSQLUm por regra e por recusa
ComponenteUma tela ou componente como o usuário vê: clicar, digitar e ver o resultadoVitest + Testing LibraryUm por comportamento da tela
Ponta a ponta (E2E)O sistema inteiro no navegador, com todos os serviços no arPlaywrightPoucos, só os fluxos principais

Um único comando roda tudo isso nos dois lados. Ele roda antes de marcar qualquer item do plano. Quando o repositório existir (Etapa 9), também vai rodar no GitHub Actions a cada push.

🐞 Regra para bugs

Encontrou um bug? Primeiro escreva um teste que o reproduza e falhe. Só então corrija. Assim, ele nunca volta sem ninguém perceber.

No fim de cada etapa, use o sistema de verdade com os usuários do seeder (Carlos, Diana, Fábio, Ana...), procurando quebrar as coisas: campos vazios, cliques duplos, acesso pela URL direta.
